# طراحی دیتابیس — بخش‌های تأییدشده

فقط ساختارهایی که مالک صریحاً تأیید کرده است. پیشنهادهای تأییدنشده در `docs/proposals/` می‌مانند.
هنوز هیچ جدولی ساخته (ORM/Migration) نشده است.

## فاز ۳: فروشندگان (تأیید ۱۴۰۵/۰۸/۲۶، دور ۱)

فهرست جدول‌های این ماژول (ساختار تفصیلی هر کدام پس از تأیید دورهای بعد اضافه می‌شود): `vendors`، `vendor_addresses`، `vendor_contacts`، `vendor_people`، `vendor_bank_accounts`، `product_categories` + `vendor_categories`، `vendor_products`، `vendor_brands`، `vendor_certificates`. فایل‌ها: موتور اسناد (فاز ۴)؛ ارزیابی: فاز ۷.

## پیش‌فرض‌های پیشنهادی (منتظر تأیید)
1. فقط نام رسمی اجباری است؛ بقیه‌ی شناسه‌ها اختیاری.
2. تکراری: هم‌شناسه‌ی ملی ← مسدود؛ نام مشابه (بدون تفاوت ي/ی، ك/ک، فاصله و نیم‌فاصله) ← فقط هشدار.
3. وضعیت‌ها: فعال، در انتظار تأیید، غیرفعال، مسدود. فروشنده‌ای که هوش مصنوعی از پیش‌فاکتور ثبت کند «در انتظار تأیید» می‌ماند.
4. نوع فعالیت: جدول مقادیر قابل ویرایش توسط مدیر (تولیدکننده، بازرگانی، واردکننده، پخش‌کننده، پیمانکار/خدماتی).
5. مدیرعامل فیلد جدا ندارد؛ در جدول اشخاص با سمت «مدیرعامل» ثبت می‌شود.


## فاز ۳: فروشندگان — دور ۲ (تأیید ۱۴۰۵/۰۸/۲۶)

تفصیل کامل جدول‌ها و پیش‌فرض‌های ۶ تا ۱۰ در `docs/proposals/vendor_round2.md` (تأییدشده): `vendor_addresses`، `vendor_people`، `vendor_contacts`، جدول مشترک `lookup_values`، قراردادهای مشترک (Audit، `is_active`، بدون حذف فیزیکی).
**اصلاح (دور ۳، تأییدشده):** `province`/`city` در `vendor_addresses` به `province_id`/`city_id` (ارجاع به `lookup_values`) تبدیل می‌شوند؛ ورودی کاربر آزاد است ولی ذخیره استاندارد.

## فاز ۳: فروشندگان — دور ۳ (تأیید ۱۴۰۵/۰۸/۲۶)

پیش‌فرض‌های ۱۱ تا ۱۶ تأیید شد: استانداردسازی با `lookup_values` (+ `parent_id`, `code`) و `lookup_aliases`، اعتبارسنجی دو سطحی، شبا یکتا و سابقه‌ی حساب‌ها، کارت تأیید و `pending_actions`.

## الف) استانداردسازی با لوکاپ و نام‌های مستعار
نرمال‌سازی همیشگی (کد): ارقام لاتین، ي/ك ← ی/ک، حذف کشیده، فاصله و نیم‌فاصله یکدست.
تبدیل به مقدار استاندارد با جدول‌های زیر؛ مثلاً «طهران، تهران، Tehran ← تهران»، «کیلو، kg ← کیلوگرم»، «بانک ملت، ملت ← بانک ملت».

- `lookup_values` (دور ۲ تأیید شده؛ **افزودن** `parent_id` و `code`): `list_key` (province, city, bank, unit, activity_type, address_type, person_role, contact_type, area_code)، `label`، `parent_id` (شهر ← استان)، `code` (مثل «019» برای کد بانک در شبا یا «021» برای کد شهر)، `sort_order`, `is_active`.
- `lookup_aliases` (جدید): `lookup_value_id`، `alias`، `alias_key` (شکل fold‌شده، یکتا در هر لیست).
- مقدار ناشناخته: پیشنهاد نزدیک‌ترین («منظورتان تهران است؟»)؛ اگر واقعاً تازه بود، در کارت تأیید به‌صورت «مقدار جدید» نشان داده می‌شود و فقط با تأیید به لیست اضافه می‌شود.
- `vendor_addresses.province`/`city` ← تبدیل به `province_id`/`city_id` (ارجاع به `lookup_values`). ورودی کاربر همچنان متن آزاد است.

## ب) قواعد اعتبارسنجی (در کد پیاده شده)
| مورد | قاعده | سطح |
|---|---|---|
| کد ملی / شناسه ملی | ۱۰ رقم (حقیقی) یا ۱۱ رقم (حقوقی) + رقم کنترل | خطا |
| کد اقتصادی | فقط رقم؛ طول ۱۲ یا ۱۴ (**تأیید نشده**) | هشدار |
| موبایل | ۱۱ رقم و ۰۹ (ارقام فارسی و +98 نرمال می‌شود) | خطا |
| تلفن ثابت | کد شهر + ۸ رقم؛ ذخیره مثل 021-12345678؛ کد شهر ← پیشنهاد شهر/استان؛ ناسازگاری با شهر اعلام‌شده ← هشدار | خطا / هشدار |
| کد پستی | ۱۰ رقم | خطا |
| شبا | IR + ۲۴ رقم + رقم کنترل (mod 97)؛ سه رقم بعد از رقم کنترل ← نام بانک | خطا |
| شماره کارت | ۱۶ رقم + Luhn | خطا |
خطا = تا اصلاح ذخیره نمی‌شود. هشدار = با تأیید کاربر.
آزمایش: الگوریتم شبا و شناسه‌ی ملی حقوقی روی مقادیر واقعی پیش‌فاکتور مالک (۴ شبا و ۱ شناسه) درست جواب داد. فهرست کد بانک‌ها «نمونه‌ی اولیه» است و باید مالک تأیید کند؛ کد ناشناخته حدس زده نمی‌شود. برای نگاشت کد شهر ← شهر/استان به فهرست رسمی نیاز داریم (بدون حدس).
