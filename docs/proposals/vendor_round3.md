# پیشنهاد دور ۳ — استانداردسازی، اعتبارسنجی و حساب‌های بانکی

**وضعیت: تأییدشده توسط مالک در ۱۴۰۵/۰۸/۲۶** (پیش‌فرض‌های ۱۱ تا ۱۶).

## اصل
داده با چت یا فایل می‌آید؛ مدل فیلدها را پر می‌کند؛ **کد** آن‌ها را نرمال، اعتبارسنجی و استاندارد می‌کند؛ کاربر **یک کارت تأیید** می‌بیند؛ سپس ذخیره می‌شود. (اپراتور فرم پر نمی‌کند.)

## الف) استانداردسازی با لوکاپ و نام‌های مستعار
نرمال‌سازی همیشگی (کد): ارقام لاتین، ي/ك ← ی/ک، حذف کشیده، فاصله و نیم‌فاصله یکدست.
تبدیل به مقدار استاندارد با جدول‌های زیر؛ مثلاً «طهران، تهران، Tehran ← تهران»، «کیلو، kg ← کیلوگرم»، «بانک ملت، ملت ← بانک ملت».

- `lookup_values` (دور ۲ تأیید شده؛ **افزودن** `parent_id` و `code`): `list_key` (province, city, bank, unit, activity_type, address_type, person_role, contact_type, area_code)، `label`، `parent_id` (شهر ← استان)، `code` (مثل «019» برای کد بانک در شبا یا «021» برای کد شهر)، `sort_order`, `is_active`.
- `lookup_aliases` (جدید): `lookup_value_id`، `alias`، `alias_key` (شکل fold‌شده، یکتا در هر لیست).
- مقدار ناشناخته: پیشنهاد نزدیک‌ترین («منظورتان تهران است؟»)؛ اگر واقعاً تازه بود، در کارت تأیید به‌صورت «مقدار جدید» نشان داده می‌شود و فقط با تأیید به لیست اضافه می‌شود.
- `vendor_addresses.province`/`city` ← تبدیل به `province_id`/`city_id` (ارجاع به `lookup_values`). ورودی کاربر همچنان متن آزاد است.

## ب) قواعد اعتبارسنجی (در کد پیاده شده)
| مورد | قاعده | سطح |
|---|---|---|
| کد ملی / شناسه ملی | ۱۰ رقم (حقیقی) یا ۱۱ رقم (حقوقی) + رقم کنترل | خطا |
| کد اقتصادی | فقط رقم؛ طول ۱۲ یا ۱۴ (**تأیید نشده**) | هشدار |
| موبایل | ۱۱ رقم و ۰۹ (ارقام فارسی و +98 نرمال می‌شود) | خطا |
| تلفن ثابت | کد شهر + ۸ رقم؛ ذخیره مثل 021-12345678؛ کد شهر ← پیشنهاد شهر/استان؛ ناسازگاری با شهر اعلام‌شده ← هشدار | خطا / هشدار |
| کد پستی | ۱۰ رقم | خطا |
| شبا | IR + ۲۴ رقم + رقم کنترل (mod 97)؛ سه رقم بعد از رقم کنترل ← نام بانک | خطا |
| شماره کارت | ۱۶ رقم + Luhn | خطا |
خطا = تا اصلاح ذخیره نمی‌شود. هشدار = با تأیید کاربر.
آزمایش: الگوریتم شبا و شناسه‌ی ملی حقوقی روی مقادیر واقعی پیش‌فاکتور مالک (۴ شبا و ۱ شناسه) درست جواب داد. فهرست کد بانک‌ها «نمونه‌ی اولیه» است و باید مالک تأیید کند؛ کد ناشناخته حدس زده نمی‌شود. برای نگاشت کد شهر ← شهر/استان به فهرست رسمی نیاز داریم (بدون حدس).

## پیش‌فرض‌های پیشنهادی (۱۱ تا ۱۶)
11. استانداردسازی با `lookup_values` + `lookup_aliases` برای استان، شهر، بانک، واحد، برند و …
12. استان و شهر در دیتابیس به‌صورت ارجاع به لیست استاندارد (ورودی آزاد، ذخیره‌ی استاندارد).
13. اعتبارسنجی دو سطحی: خطا (شبا، شناسه‌ها، موبایل، کد پستی، کارت) و هشدار (کد اقتصادی، ناسازگاری کد شهر).
14. بانک از شبا، و شهر/استان پیشنهادی از کد تلفن ثابت.
15. شبا یکتا در کل سیستم (یک شبا دو فروشنده نداشته باشد)؛ تغییر حساب = سطر تازه و غیرفعال‌شدن قدیمی (سابقه حفظ)؛ شبا کامل فقط برای نقش‌های مجاز.
16. ورود اطلاعات: مدل پر می‌کند، کارت تأیید واحد نشان داده می‌شود، پیش‌نویس تا تأیید در جدول `pending_actions` (هسته‌ی فاز ۲) می‌ماند.
