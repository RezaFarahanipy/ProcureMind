# معماری: وضع فعلی و چشم‌انداز

## ۱. وضع فعلی (فاز ۱: ابزار آزمایش، نه رابط نهایی)

```
کاربر ── پیام / فایل (+) ──► رابط چت (frontend/index.html، فقط برای تست)
                                  │
              ┌───────────────────┴────────────────────┐
              ▼                                         ▼
   استخراج متن از فایل                              گفت‌وگوی عادی با مدل چت
   • لایه متنی PDF (راست‌به‌چپ + جدول)              (لحن گرم، نام کاربر)
   • دستی (Google Lens) + نرمال‌سازی
   • Dots OCR / PaddleOCR (کند یا ضعیف)
              │
              ▼
   تشخیص نوع سند (قاعده‌محور؛ backend/doc_classifier.py)
              │ پیش‌فاکتور
              ▼
   جدول اقلام با کد (حساب‌محور؛ backend/invoice_parser.py)  ──┐
   سربرگ: شماره/تاریخ/ارز/خریدار با regex + فروشنده از مدل  ──┤► نتیجه + بررسی خودکار حساب‌ها
   (ادعای مدل با متن سند تطبیق داده می‌شود)                  ──┘
```
هنوز: دیتابیس، کاربر و نقش، جدول فروشندگان، ثبت پیش‌فاکتور، اقدام خودکار، گردش تأیید **وجود ندارند**.

## ۲. چشم‌انداز: «فایل را بده؛ خودش بفهمد و کار را پیش ببرد»

۱. دریافت فایل و ذخیره‌ی اصلی ← ۲. استخراج متن ← ۳. تشخیص نوع سند ← ۴. استخراج ساختاریافته (جدول با کد، سربرگ با مدل) ←
۵. **تطبیق با دیتابیس** (مثلاً «این فروشنده در بانک فروشندگان نیست») ← ۶. **پیشنهاد اقدام** («فروشنده را ثبت کنم؟ پیش‌فاکتور را به پروژه X وصل کنم؟») ←
۷. **اجرا پس از تأیید کاربر** + ثبت در Audit Log.

قواعد (طبق سند دستورالعمل): مدل SQL آزاد اجرا نمی‌کند؛ فقط ابزارهای تعریف‌شده‌ی بک‌اند (جست‌وجوی فروشنده، ثبت فروشنده، ثبت پیش‌فاکتور، …) را صدا می‌زند؛ مجوزهای AI همان مجوزهای کاربر است؛ عملیات حساس بدون تأیید اجرا نمی‌شود؛ عدد مالی را کد حساب می‌کند نه مدل.

پیش‌نیاز مراحل ۵ تا ۷: طراحی و تأیید جدول‌های فروشندگان (فاز ۳) و درخواست/استعلام/پیش‌فاکتور (فاز ۵) طبق پروتکل بخش ۷ سند (پیشنهاد، سؤال، تأیید، سپس ساخت).

## ۳. گفتگوی روان و شخصی‌سازی
- فعلاً: نام کاربر در تنظیمات (ذخیره در مرورگر) و پرامپت سیستم گرم برای چت آزاد.
- بعداً (به تصمیم مالک): «حافظه» فقط برای ترجیحات کاربر؛ بقیه‌ی اطلاعات در دیتابیس. نام کاربر از حساب کاربری می‌آید (فاز ۲).

## ۴. رابط نهایی
رابط فعلی یک HTML ساده برای تست مدل‌هاست. رابط واقعی طبق سند: React + TypeScript + Tailwind + shadcn/ui + Framer Motion، فونت SG Kara، چت‌محور با انیمیشن و طراحی حرفه‌ای (فاز ۲). پیشنهاد: قبل از کدنویسی، نمونه‌ی طراحی برای تأیید ظاهر ساخته شود.

## ۵. مدل‌های مسیریابی/تصمیم (برای بررسی بعدی)
مدل‌های خانواده‌ی «laya» و «DibaOne» (طبق کارت‌هایشان) مدل‌های کوچک «انتخاب/طبقه‌بندی» هستند، نه مدل چت؛ می‌توانند برای تشخیص نوع سند و انتخاب ابزار (مسیریابی) در موارد مبهم کنار قواعد استفاده شوند. ادعاهای کارت‌ها روی اسناد ما تأیید نشده است.
