## ۱۴۰۵/۰۸/۲۶ — نتیجه تست PDF دیجیتال و بهبود لایه متنی
- گزارش مالک: خواندن لایه متنی PDF (پیش‌فاکتور سیستم حسابداری) خیلی خوب و سریع بود؛ OCR (Paddle fa) سریع‌تر از Dots ولی پر از غلط بود. جمع‌های سند نمونه با حساب دستی تطبیق داده شد (سطرها، جمع کل، مالیات).
- مشکلات متن خام: حروف به شکل‌های نمایشی یونیکد (U+FE70..)، ستون‌های جدول چسبیده («کیلوگرم693»)، ترتیب تکه‌های راست‌به‌چپ جابه‌جا. اصلاح: `normalize_fa` + `layout_text` (پیش‌فرض `text_style=layout`، گزینه خام برای مقایسه). فقط با PDF ساختگی تست شد؛ روی PDF واقعی مالک هنوز تأیید نشده.
- جهت پیشنهادی: PDF دیجیتال ← لایه متنی؛ اسکن/عکس ← OCR (انتخاب موتور بعد از تست فارسی).
- PDF واقعی مالک (پیش‌فاکتور پارمیس) بررسی شد: روش کلمه‌به‌کلمه کلمات را می‌شکست («ماها ن»). `layout_text` به روش حرف‌به‌حرف بازنویسی شد؛ خروجی روی همان PDF: ردیف‌های جدول، ترتیب راست‌به‌چپ، اعداد و واحدها درست. باقی‌مانده: سرستون‌های چندخطی تکه‌تکه، «693 | متر» در دو سلول.
- مالک گزارش داد Qwen3.5-9B روی CPU خیلی کند است (۶۱۷ ثانیه، اولین توکن ۲۲۸ ثانیه، ۱.۵۸ توکن/ثانیه، RAM ≈۱۵.۵GB یعنی فشار حافظه)؛ خروجی JSON خوب ولی با خطا (نشانی و موبایل فروشنده/خریدار قاطی شد، نام کالا ناقص) و ناتمام.

## ۱۴۰۵/۰۸/۲۶ — نتیجه Qwen3.5-4B
- مالک: Qwen3.5-4B روی متن مرتب‌شده‌ی پیش‌فاکتور واقعی: ۱۹۲ ثانیه (اولین توکن ۶۲.۶، ۲.۶۶ توکن/ثانیه) در برابر ۹B: ۶۱۷ ثانیه (۲۲۷.۷، ۱.۵۸). فروشنده، شماره، تاریخ، ارز، جمع کل و null ها درست. اشتباه: «مقدار اصلی/فرعی» قاطی شد (ردیف ۳: ۱۹۰ شاخه به‌جای ۱۵۲۰ کیلوگرم؛ فی به ازای کیلوگرم است) و کد کالا داخل نام آمد.
- اصلاح: پرامپت «پیش‌فاکتور» (qty/unit اصلی، sub_qty/sub_unit، code جدا، JSON فشرده) و `checkInvoice` در `frontend/index.html` که ضرب تعداد×فی و جمع‌ها را خودکار چک می‌کند و زیر پاسخ هشدار می‌دهد. روی خروجی ۴B واقعی ردیف ۳ را درست گرفت.
- ایده بعدی (منتظر تأیید): جدول را با کد (قاعده/ستون‌یابی) بخوان و Qwen فقط برای سربرگ و نگاشت ستون‌ها.
